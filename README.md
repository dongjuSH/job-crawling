# 채용정보 크롤링 스터디 노트

> 채용 공고 트렌드 분석 대시보드 프로젝트 — 데이터 수집 방식 검토 및 구현 기록

## 노트 (1) — 크롤링이란 무엇인가

### 1. 크롤링이란?

#### 용어부터 구분하기

| 용어 | 뜻 |
|---|---|
| **스크래핑(Scraping)** | 페이지 **하나**에서 원하는 정보를 추출하는 행위 자체 |
| **크롤링(Crawling)** | 여러 페이지를 자동으로 돌아다니며(링크를 따라가며) 스크래핑을 **반복**하는 과정/프로그램 |
| **크롤러(Crawler)** | 크롤링을 수행하는 프로그램(봇) 그 자체를 부르는 말 |

#### 왜 생겨났나

크롤러는 원래 구글 같은 검색엔진이 전 세계 웹페이지를 찾아다니며 **색인(Index, 검색 가능하도록 내용을 정리해서 저장해두는 것)** 을 만들기 위해 만들어졌습니다. 최근에는 검색엔진뿐 아니라 AI 모델을 학습·운영하는 회사들도 콘텐츠 수집을 위해 크롤러를 운영하고 있습니다. 이 기술이 일반화되면서, **공개 API가 없는 사이트에서 데이터를 자동으로 가져오려는 목적**(가격 비교, 뉴스 수집, 그리고 우리가 하려는 채용정보 수집 등)으로도 널리 쓰이게 됐습니다.

### 2. 작동 원리 및 구현 방법

#### 기본 파이프라인

1. **요청(HTTP Request)**: 대상 URL에 "이 페이지 주세요"라고 요청을 보내 HTML을 받아옴
   - *HTTP 요청/응답*: 클라이언트(크롤러)가 서버에 보내는 게 요청(Request), 서버가 돌려주는 게 응답(Response). `GET`은 조회용, `POST`는 데이터 제출용 요청 방식
   - 파이썬에서는 `requests` 라이브러리를 주로 사용
2. **파싱(Parsing)**: 받은 HTML 문자열을 컴퓨터가 다루기 쉬운 구조(트리 형태의 객체, **DOM**)로 분해·해석
   - *DOM(Document Object Model)*: HTML 문서를 태그들이 부모-자식 관계로 얽힌 트리 구조로 표현한 것
   - 파이썬에서는 `BeautifulSoup`, `lxml` 등을 사용해 `find()`, `find_all()`, CSS 셀렉터 등으로 원하는 태그를 찾음
3. **순회(Traversal)**: 목록 페이지 → 상세 페이지 링크를 따라가거나, **페이지네이션**(1페이지, 2페이지... 형태로 목록을 나눠 보여주는 방식)을 반복하며 URL의 페이지 번호를 바꿔가며 요청
4. **저장**: 추출한 데이터를 CSV/JSON 파일 또는 DB에 적재
5. **(필요시) 동적 렌더링 대응**: 사이트가 **SPA(Single Page Application, 페이지 이동 없이 자바스크립트가 화면 일부만 동적으로 바꿔 그리는 방식 — React/Vue 기반 사이트 대부분 해당)** 구조라면, 1~4번 방식으론 데이터가 채워지기 전의 빈 HTML만 받아지므로 `Selenium`, `Playwright` 같은 도구로 실제 브라우저를 띄워 렌더링이 끝난 뒤의 화면을 읽어야 함

#### 참고: 크롤링 도구 비교

| 도구 | 용도 |
|---|---|
| `requests` | HTML/API 응답을 가져오는 HTTP 요청 라이브러리 |
| `BeautifulSoup` | HTML을 파싱해서 원하는 데이터를 찾는 라이브러리 (그 자체로는 요청 기능 없음 → `requests`와 세트로 사용) |
| `Selenium` / `Playwright` | 실제 브라우저를 코드로 조작 — 로그인, 클릭, SPA 렌더링 대기 등이 필요할 때 사용 |
| `Scrapy` | 요청+파싱+저장까지 통합된 크롤링 전용 프레임워크 (대규모/반복 크롤링에 적합, 학습 곡선 있음) |

### 3. 추가로 알면 좋은 내용

#### robots.txt — 사이트가 크롤러에게 남기는 규칙

**robots.txt**는 1994년 제정된 로봇 배제 표준으로, 웹 크롤러 같은 봇들이 사이트의 어떤 부분에 접근해도 되는지를 명시한 파일입니다. 확인 방법은 간단합니다 — 사이트 도메인 뒤에 `/robots.txt`를 붙이면 됩니다. (예: `https://www.saramin.co.kr/robots.txt`)

- `Allow`: 접근을 허용하는 페이지/경로
- `Disallow`: 접근을 막는 페이지/경로
- `Crawl-delay`: 요청 사이에 최소 몇 초를 기다려야 하는지 지정 (단, 구글은 이 지시를 인식하지 않음)

**중요**: robots.txt는 법적 강제력이 있는 게 아니라 크롤러가 자율적으로 따르는 "권고"입니다. 즉 robots.txt가 막고 있어도 기술적으로 접속 자체가 차단되는 건 아니지만, 이를 무시하고 진행하면 사이트 운영자와의 분쟁이나 법적 문제로 이어질 수 있는 신호로 봐야 합니다.

#### 저작권·법적 리스크

2016년 개정된 한국 저작권법 제30조는 정보 해석(사적 이용 등)을 목적으로 한 저작물의 복제·번안을 허용하고 있습니다. 다만 이는 "학습·분석 목적"에 대한 제한적 예외이지, **이용약관 위반이나 상업적 재배포까지 면책해주는 것은 아닙니다.** 채용정보 사이트 대부분은 이용약관에 "무단 수집·크롤링 금지" 조항을 두고 있는 경우가 많으므로, robots.txt 확인과 이용약관 확인을 반드시 함께 진행해야 합니다.

#### "사람처럼 보이기"가 필요한 이유

많은 사이트는 서버 부하를 줄이고, 콘텐츠 무단 수집을 막고, 봇으로 인한 트래픽 폭주를 방지하기 위해 **봇 탐지 시스템**을 운영합니다. 짧은 시간에 반복적으로 같은 패턴의 요청이 들어오거나, **User-Agent**(요청을 보내는 주체가 "나는 크롬 브라우저다" 혹은 "나는 파이썬 스크립트다"라고 밝히는 헤더 정보)가 기본값 그대로 노출되거나, 사람이라면 낼 수 없는 속도로 페이지를 넘기면 — 이런 요청은 곧바로 자동 탐지되어 **IP 차단, 403 요청 거부, 캡차 요구**로 이어집니다.

즉 "사람처럼 보이기"는 크롤러가 몰래 속이기 위한 편법이 아니라, **정상적인 브라우저 접속과 구분되지 않는 자연스러운 요청 패턴을 만들어 서버 부담을 줄이고 안정적으로 데이터를 받아오기 위한 최소한의 기술적 요건**입니다. 이를 신경 쓰지 않으면 코드가 문법적으로 맞아도 몇 번 요청하다 바로 차단되어 데이터를 거의 수집하지 못하는 상황이 생깁니다.

실무에서 챙기는 것들:

- **요청 사이에 딜레이(sleep) 주기**: 초당 수십 건씩 요청하는 패턴은 봇으로 즉시 식별됨
- **User-Agent 헤더를 실제 브라우저처럼 설정**: 기본 라이브러리 값 그대로 보내면 요청 자체에 "나는 스크립트"라고 써 붙이는 셈
- **쿠키 포함 여부 확인**: 로그인/세션 기반 사이트는 쿠키 없는 요청을 비정상으로 간주해 차단하는 경우가 많음
- **POST 요청 시 서버가 기대하는 모든 필드(hidden 필드 포함)를 함께 전송**: 일부 필드 누락은 정상 사용자 요청과 달라 보여 거부될 수 있음
- **크롬 개발자도구 Network 탭으로 실제 요청 형태 확인**: 브라우저가 실제로 보내는 헤더·파라미터를 그대로 재현하기 위한 확인 절차
- **403 Forbidden 에러 발생 시**: 대부분 IP가 이미 차단됐다는 신호 → 딜레이를 늘리거나 접근 방식 재검토 필요

> ⚠️ 위 기법들은 봇 탐지를 피해가는 기술이므로, robots.txt·이용약관에서 명시적으로 크롤링을 금지한 사이트에 적용하는 것은 기술적으로는 가능해도 **법적·윤리적으로는 문제가 될 수 있습니다.**

### 5. 요약

**크롤링이란**, 사람이 직접 검색하고 특정 페이지로 넘어가는 행동을 봇이 자동으로 반복하면서 정해진 사이트들을 돌아다니며 필요한 정보를 가져오는 것이다. 이 과정은 파이썬 환경에서 구축 가능하며, 정보를 가져올 때는 사이트의 HTML을 받아와서 컴퓨터가 가공하기 쉬운 구조(파싱)로 바꾼 뒤 CSV/JSON 형식(또는 DB)으로 저장한다.

**문제는**, 각 사이트가 크롤러 같은 봇에게 접근 규칙(`robots.txt`)을 명시해두는데, 이를 어길 경우 IP 차단부터 크게는 법적 문제까지 번질 수 있다는 점이다.

이를 막는 절차는 순서가 중요하다 — "사람처럼 보이기"가 문제를 막아주는 게 아니라, **애초에 규칙을 위반하지 않는 것**이 법적 리스크를 막는 방법이다.

1. **robots.txt / 이용약관 확인** → 애초에 이 사이트를 크롤링해도 되는지 판단 (법적 리스크 방지)
2. **허용된 범위 안에서** → 딜레이 주기, 실제 브라우저처럼 헤더(User-Agent 등) 설정 등으로 "사람처럼 보이게" 요청 → 봇 탐지로 인한 IP 차단을 막고 안정적으로 데이터 수집 (기술적 안정성 확보)

즉 1번은 **해도 되는지**를 판단하는 단계이고, 2번은 **허용된 것을 잘 가져오기 위한** 기술적 조치다. 이 둘을 혼동하면 "허가 안 된 사이트를 기술적으로 안 들키게 크롤링하는 것"이 괜찮다고 오해하기 쉬우므로 주의.

### 1. 사이트별 크롤링 가능성 판단

#### robots.txt 확인 결과

| 사이트 | robots.txt 확인 결과 |
|---|---|

- **참고 반례**: 2022년 대법원은 숙박업 정보 크롤링 형사사건에서는 무죄를 확정한 사례도 있음 — **수집 규모·빈도, 명시적 금지 여부, 차단 후 재접속 여부, 상업적 경쟁 이용 여부**가 위법성 판단의 핵심 기준.
- **결론**: 사람인·잡코리아는 채용정보 크롤링 관련 확정 판례가 존재하는 도메인이라 리스크가 명확함. 원티드는 직접 판례는 없으나 유사 업계 특성상 동일 선상에서 봐야 함.

#### 최종 선택: 고용24 (work24.go.kr)

- robots.txt상 가장 개방적
- 정부(고용노동부·한국고용정보원) 운영 공공기관 사이트로, 상업적 경쟁사 간 분쟁이었던 기존 판례와는 성격이 다름
- 고용24 화면에 **사람인·잡코리아·인크루트 등 민간 사이트 공고가 이미 합법적으로 중계·게재**되고 있음을 확인 → 고용24만 크롤링해도 민간 사이트 공고 상당수를 정부 공식 채널을 통해 확보 가능

### 2. 구현 방법

#### 2-1. 페이지 구조 확인

대상 페이지: `https://m.work24.go.kr/wk/a/b/1200/retriveDtlEmpSrchList.do`

이 페이지는 **서버사이드 렌더링** 방식이라 접속하는 순간 실제 채용정보가 HTML에 그대로 담겨 내려온다. React 등 SPA가 아니므로 `Selenium` 없이 `requests` + `BeautifulSoup`만으로 수집 가능.

#### 2-2. F12 개발자도구로 검색 요청 캡처하는 방법

1. 대상 페이지에서 F12(개발자도구) → **Network 탭** 열기
2. 필터를 **All**로 설정 (검색 결과가 AJAX가 아니라 파라미터를 포함한 페이지 재요청 형태로 오는 경우가 있어, XHR/Fetch로만 좁히면 놓칠 수 있음)
3. 원하는 조건(지역, 직종 등)을 선택하고 **검색 버튼 클릭**
4. Network 목록에서 Type이 `document`인 요청을 찾아 클릭
5. **Headers 탭**에서 Request Method(GET/POST) 확인
   - GET이면 주소창의 URL 자체에 파라미터가 `?key=value&...` 형태로 포함되어 있음
   - POST면 **Payload(Form Data)** 탭에서 전송된 파라미터 확인
6. 이 파라미터를 그대로 파이썬 `requests` 요청에 재현

#### 2-3. 직종 코드 확정 (한국고용직업분류 기준)

고용24는 **한국고용직업분류(KECO)** 체계를 사용한다. 상세검색 화면의 1차 분류 중 IT(소프트웨어+하드웨어)에 해당하는 항목은 아래와 같이 확인됨.

**"연구 및 공학기술" → 2차 분류**
- 소프트웨어
- 컴퓨터시스템
- 컴퓨터하드웨어·통신공학
- 네트워크 시스템 및 정보보안
- 데이터 및 정보시스템·웹 운영

**"설치·정비·생산-전기·전자·정보통신" → 2차 분류**
- 방송·통신장비 및 케이블 설치·수리
- 정보통신기기 설치·수리(컴퓨터,핸드폰)

위 7개 항목만 체크하고 검색 시, `occupation` 파라미터에 해당 코드가 콤마로 결합되어 전달됨 (예: `106,107,025,026,024,023,022`). 그 외 전기·전자 일반, 전력설비, 가전 A/S, 건설·화학 등은 IT와 무관하므로 체크하지 않음.

#### 2-4. 확정된 요청 파라미터

```
GET https://m.work24.go.kr/wk/a/b/1200/retriveDtlEmpSrchList.do

occupation = 106,107,025,026,024,023,022   # IT 직종 코드
occupationParam = (occupation과 동일한 값)
region / regionParam / codeDepth1Info / codeDepth2Info = 11000   # 서울
resultCnt = 100        # 페이지당 결과 수
currentPageNo / pageIndex = 페이지 번호 (반복 요청 시 증가)
sortField = DATE, sortOrderBy = DESC   # 최근 등록순
siteClcd = all          # 전체 정보제공처(고용24+사람인+잡코리아+인크루트 등)
```

그 외 다수 파라미터는 값이 비어있지만, 실제 브라우저 요청과 동일한 파라미터 목록을 전부 포함해야 서버가 정상 응답한다.

#### 2-5. 크롤러 코드 구조 (`work24_crawler.py`)

- `fetch_list_page(params)`: GET 요청 + BeautifulSoup 파싱
- `extract_jobs(soup)`: 상세페이지 링크(`a[href*='empDetailAuthView']`)를 기준점으로 삼아, 그 링크를 감싸는 `<tr>`/`<li>`를 거슬러 올라가 행 전체 텍스트를 추출. 정확한 CSS 클래스명이 없어도 동작하도록 설계.
  - `wanted_auth_no`(공고 고유 ID)를 링크에서 추출 → DB 적재 시 중복 방지 키로 사용
  - `raw_row_text`: 회사명/기업규모/급여/경력/학력/지역/마감일/등록일이 `" | "`로 구분되어 한 문자열에 담김 (다음 단계에서 정규식으로 필드 분리 예정)
- `run_crawler(max_pages, delay_sec)`: 페이지네이션 순회, 요청 간 딜레이(기본 1.5초, "사람처럼 보이기" 목적), `wanted_auth_no` 기준 중복 제거
- `save_to_json` / `save_to_csv`: 결과 저장 (JSON 기본, CSV는 필요시 주석 해제)

---

### 3. 실행 방법

```bash
pip install requests beautifulsoup4 pandas
python work24_crawler.py
```

기본값은 서울 + IT 직종, 1페이지(100건) 테스트 수집 후 JSON으로 저장. `run_crawler(max_pages=...)` 값을 조정해 수집 범위 변경 가능.
